Introduction

What is R, and why does UGC NET test it?

R is a free, open-source programming language and environment built specifically for statistical computing and graphics. Unlike a general-purpose language pressed into service for data work, R was designed from day one by statisticians, for statistics: its vectors, its built-in probability distributions, its modelling syntax (y ~ x) and its graphics device all read like the notation you'd already find in a statistics textbook. That closeness to statistical thinking — plus the fact that it is free and runs identically on Windows, macOS and Linux — is why R sits inside the "Research Methodology / Computer Applications" units of exams like UGC NET Statistics, Population Studies, Commerce, Economics and Management, rather than being treated as a generic "programming" elective.

The syllabus line reproduced at the top of this guide is deliberately narrow: it is not asking you to become a software engineer, it is asking whether you can read and predict the output of short R snippets — a calculator expression, a loop, a matrix multiplication, a data-management one-liner — the way a working data analyst does every day. NET question-setters lean hard on this: almost every R question in past papers is a "what does this print?" or "put these lines in the right order" question, not an essay question. That is exactly the format this guide drills.

Two more things are worth knowing before you dive in. First, R is interpreted and vectorised: there's no separate compile step, and operations you might loop over in other languages usually apply to a whole vector at once — this single idea (covered in Unit 2) explains a surprising fraction of "surprising" R output. Second, R's power comes overwhelmingly from its package ecosystem — tens of thousands of add-on libraries hosted on CRAN, Bioconductor and elsewhere — so a working knowledge of where packages come from and how they're vetted (covered later in this section) is itself fair examination territory.

This guide is organised in three layers: the ecosystem (history, IDEs, versions, repositories — background context), the ten syllabus units (the actual R language, syntax by syntax), and practice (verified previous-year questions plus 20 fresh ones). Use the sidebar to jump straight to whichever layer you need.

The R ecosystem

History of R

R's lineage runs through one earlier language: S, designed at Bell Laboratories by John Chambers and colleagues from 1976 onward as an interactive language for data analysis. R was written as a free, open-source reimplementation of S's ideas — enough so that, as the R Project itself puts it, "most code written for S runs unaltered under R."

The R ecosystem

R IDEs and development tools

R itself is just a language and an interpreter — R or Rscript at a terminal is enough to run any program in this guide. In practice, almost everyone works through an editor or IDE that wraps the console with a script pane, an object browser, plotting and package management. Here are the ones you'll actually meet.

RStudio (now under Posit)

First released in 2011 by JJ Allaire, RStudio is by far the most widely used R IDE: a four-pane layout (script, console, environment/history, plots-packages-help), tight integration with R Markdown/Quarto, Git, Shiny and package-building tools. The company behind it, RStudio PBC, renamed itself Posit PBC on 2 November 2022 to reflect its broadened focus on Python as well as R — but the IDE product itself kept the name "RStudio". Both the free RStudio Desktop and the enterprise Posit Workbench/Connect trace back to it.

Positron

Posit's next-generation IDE, built on the same open-source platform as VS Code (Code OSS). Positron treats R and Python as equal first-class languages side by side, borrows VS Code's extension ecosystem, and supports Jupyter-style notebooks natively. It entered public preview in July 2024 and reached general availability in August 2025 — positioned to eventually sit alongside, not immediately replace, RStudio.

VS Code + R extension

Microsoft's Visual Studio Code, fitted with the community "R" extension (REditorSupport) plus the languageserver and httpgd packages, gives R users VS Code's debugging, Git and multi-language tooling — popular on teams that mix R with Python, SQL or web code.

Jupyter Notebook / JupyterLab

Installing the IRkernel package lets R run inside Jupyter's notebook cells — the same interleaved code/output/markdown format most people first meet through Python, usable for R just as well.

Base R GUIs

Rgui.exe on Windows and the "R Console" app (R.app) on macOS ship with base R itself — a minimal script editor plus console and graphics window, no separate install needed. The plain command-line R / Rscript is available everywhere, including every Linux server.

Editor integrations

ESS (Emacs Speaks Statistics) and Nvim-R/Vim-R bring a live R console into Emacs and Vim respectively; Eclipse StatET does the same for Eclipse — all popular with users who already live in those editors.

Point-and-click front ends

R Commander (the Rcmdr package), Jamovi and JASP give menu-driven, SPSS-like interfaces for users who don't want to type code — all three run R underneath and can show you the generated R syntax, making them a common on-ramp into "real" R.

Cloud & notebook platforms

Posit Cloud hosts full RStudio sessions in a browser with no local install; Google Colab and Kaggle Notebooks can both run an R kernel for quick, shareable, zero-setup analysis.

Exam trap The stringsAsFactors default flip in R 4.0.0 (2020) is the single most-tested version-history fact: before 4.0.0, data.frame() converted character columns to factors by default; from 4.0.0 onward the default is FALSE, so character columns stay character unless you ask otherwise. Equally testable: the native pipe |> arrived in 4.1.0 (2021), not with the much older magrittr pipe %>%, which is a tidyverse package operator, not a base-R one.
The R ecosystem

CRAN, Bioconductor & other package repositories

Base R is deliberately small; almost everything beyond core language features arrives as a package. Where a package comes from, and how rigorously it was checked before you can install it, is itself part of the "R software" picture.

CRAN — the Comprehensive R Archive Network

Founded in 1997 by Kurt Hornik and Friedrich Leisch, CRAN is R's default, general-purpose package repository — and the network of mirror servers that hosts it worldwide. It started with 3 mirrors and 12 packages; by 2026 it has grown to roughly 90 mirrors and more than 22,900 packages covering every domain from finance to ecology to machine learning. Every package submitted to CRAN is automatically run through R CMD check across multiple operating systems and R versions before acceptance, and again on an ongoing schedule afterward — packages that start failing checks (e.g. after an R release changes some behaviour) can be archived until fixed.

> install.packages("ggplot2")     # fetch & install from CRAN
> update.packages()               # refresh everything to the latest CRAN version
> library(ggplot2)                # load it into the session

Bioconductor

Bioconductor is a separate, specialised repository launched in Fall 2001, dedicated to software for the analysis of genomic and molecular-biology data — sequencing, microarrays, single-cell transcriptomics, and similar. It holds itself to a stricter bar than CRAN: mandatory vignettes (worked tutorials), a formal peer-review process for new submissions, and a release train that moves in lock-step with R itself — two Bioconductor releases a year, each one built and tested against a specific R version (Bioconductor 3.23, for instance, pairs with R 4.6 and ships around 2,400 packages). Because it isn't on CRAN, Bioconductor has its own installer:

> install.packages("BiocManager")   # one-time: get the Bioconductor installer
> BiocManager::install("DESeq2")    # installs from Bioconductor, not CRAN

Other sources

SourceWhat it's for

Exam-relevant fact Know the installer-to-repository pairing: install.packages() talks to CRAN (or a CRAN-like mirror) by default; Bioconductor packages need BiocManager::install() instead; GitHub-only packages need remotes/devtools. A question that names "the repository dedicated to genomic data analysis, releasing twice yearly alongside R" is describing Bioconductor.
Unit 1

R as a calculator

Before it is a statistics package, R is a calculator you talk to at a prompt (>). Every expression you type is evaluated immediately and printed, unless you assign it to a name.

Arithmetic operators

Precedence, high to low: ^ > unary - + > %% %/% > * / > binary + - > comparisons > ! > & && > | || > ~ > -> > <-. Exponentiation is right-associative, so 2^3^2 is 2^(3^2) = 512, not (2^3)^2.

> 2 + 3 * 4        # * before +
[1] 14
> (2 + 3) * 4
[1] 20

[1] -4
> (-2)^2
[1] 4
> 17 %% 5           # remainder
[1] 2
> 17 %/% 5          # quotient
[1] 3

Assignment: three spellings, one meaning

<- is the idiomatic R assignment operator; = also assigns at the top level; -> assigns left-to-right. Inside a function call, = is reserved for naming arguments, so mean(x = c(1,2,3)) names the argument, while mean(x <- c(1,2,3)) both creates x in your workspace and passes it to mean().

> a <- 5
> 10 -> b
> a + b
[1] 15

Exam trap round() uses "round half to even" (IEC 60559), not the "round half up" rule taught in school arithmetic. So round(0.5) is 0, round(1.5) is 2, and round(2.5) is 2 — each goes to the nearest even digit. NET question-setters exploit this regularly.
Practice — What does R print for 5 %/% 2 + 5 %% 2 * 2?
  1. 5
  2. 3
  3. 4
  4. 7
Why: %%/%/% bind tighter than *//, which in turn bind tighter than +. So R first reduces 5 %/% 2 → 2 and 5 %% 2 → 1, leaving 2 + 1 * 2; then * before + gives 2 + 2 = 4.
Unit 2

Vectors, functions & matrix operations

Everything in R is a vector at heart — even a single number is a vector of length 1. c() ("combine") builds one.

> x <- c(1, -1, 3.5, 2)
> x
[1]  1.0 -1.0  3.5  2.0
> length(x)
[1] 4
> x[2]                 # 1-based indexing
[1] -1
> x[c(1,3)]            # select multiple elements
[1] 1.0 3.5
> x[-1]                # drop the first element
[1] -1.0  3.5  2.0
> x[x > 0]             # logical (boolean) subsetting
[1] 1.0 3.5 2.0

The recycling rule

When two vectors of unequal length are combined arithmetically, R silently recycles the shorter one — repeating it from the start until it matches the longer vector's length. If the longer length isn't an exact multiple of the shorter, R still does it but issues a warning.

> c(1,2,3,4) + c(10,20)
[1] 11 22 13 24
> c(1,2,3) + c(10,20)   # length 3 is not a multiple of 2
[1] 11 22 13
Warning message: longer object length is not a multiple of shorter object length
Exam trap — matrix × vector Recycling also governs matrix * vector. R stores a matrix internally as one long column-major vector, so a numeric vector multiplied against a matrix is recycled down that column-major order. If the vector's length equals the number of rows, this has the visual effect of "multiply each row by the matching scalar" — but it is really just recycling, not true matrix algebra.
Worked example 
> A <- matrix(c(1:9), 3, 3)
> A
     [,1] [,2] [,3]
[1,]    1    4    7
[2,]    2    5    8
[3,]    3    6    9
> x <- c(1, 2, 3)
> y <- A * x        # element-wise, recycled column-major
> y
     [,1] [,2] [,3]
[1,]    1    4    7
[2,]    4   10   16
[3,]    9   18   27
> diag(y)
[1]  1 10 27
Column 1 of A (1,2,3) is multiplied elementwise by x = (1,2,3); the same x then recycles down columns 2 and 3. Only the diagonal — row i, column i — happens to equal A[i,i] * x[i], giving 1×1, 5×2, 9×3 = 1, 10, 27.

> diag(3)                  # n = 3 -> 3x3 identity
     [,1] [,2] [,3]
[1,]    1    0    0
[2,]    0    1    0
[3,]    0    0    1
> diag(c(2,5,9))            # vector -> diagonal matrix

Practice — A <- matrix(1:6, nrow = 2). What is dim(A)?
  1. c(6, 1)
  2. c(2, 3)
  3. c(3, 2)
  4. c(1, 6)
Why: nrow = 2 is given explicitly; R infers ncol = length(data)/nrow = 6/2 = 3. Fill order is column-major: col1 = (1,2), col2 = (3,4), col3 = (5,6).
Practice — For square matrices A, B of the same size, which is generally FALSE?
  1. t(A %*% B) equals t(B) %*% t(A)
  2. A %*% B equals B %*% A
  3. det(A %*% B) equals det(A) * det(B)
  4. solve(solve(A)) equals A (when A is invertible)
Why: matrix multiplication is not commutative in general — this is a classical-algebra fact R inherits directly, and NET loves testing it disguised as an R question.

Exam trap var() and sd() in R divide by n−1 (the unbiased/sample formula), never by n. If a question gives population variance by the 1/n formula and asks "what does R's var() return", you must rescale: R's var = population var × n / (n−1).
Practice — What does class(1L) return, and how does it differ from class(1)?
  1. Both return "numeric"
  2. "integer" for 1L, "numeric" for 1
  3. Both return "double"
  4. "integer" for both
Why: the L suffix forces the integer storage type; a bare numeral like 1 is stored as a double-precision "numeric" by default.

Unit 5

Conditional execution & loops

if / else and vectorised ifelse()

> mark <- 42
> if (mark >= 40) print("Pass") else print("Fail")
[1] "Pass"

> scores <- c(38, 55, 40, 12)
> ifelse(scores >= 40, "Pass", "Fail")   # vectorised, no loop needed
[1] "Fail" "Pass" "Pass" "Fail"

switch()

> grade <- function(g) switch(g,
+   "A" = "Excellent",
+   "B" = "Good",
+   "Needs work")                          # unmatched -> default (last, unnamed)
> grade("B"); grade("Z")
[1] "Good"
[1] "Needs work"

Loops: for, while, repeat

> total <- 0
> for (i in 1:5) total <- total + i
> total
[1] 15

> n <- 1
> while (n^2 < 50) n <- n + 1
> n
[1] 8

> k <- 0
> repeat {
+   k <- k + 3
+   if (k > 10) break
+ }
> k
[1] 12

next skips to the following iteration; break exits the loop entirely. A repeat loop has no built-in stopping condition — you must break out of it, or it runs forever.

Worked example — this exact program appeared as UGC NET Q.122 
> f <- function(n) {
+   x = 1
+   for (i in 1:n) {
+     x = x * i
+   }
+   x
+ }
> f(5)
[1] 120
This is an iterative factorial: x accumulates 1×1×2×3×4×5 = 120. The last line of a function body (here, bare x) is its return value — no explicit return() is required.
Exam trap — function-local scope A variable created with <- or = inside a function body is local to that call. It shadows a same-named variable in the global environment for the duration of the call and vanishes afterwards — the outer variable is untouched.
Worked example — this exact program appeared as UGC NET Q.108 
> x <- 3
> f <- function(y) {
+   x <- 5      # local x, shadows the global x
+   x + y
+ }
> f(4)
[1] 9
> x             # global x is unaffected
[1] 3
Inside f, x <- 5 creates a fresh local binding; the function returns 5 + 4 = 9. The global x is still 3 once f() returns. (To modify the global from inside a function on purpose, you'd need the "superassignment" operator <<- instead of <-.)
Practice — What is printed?
x <- 1; f <- function(){ x <<- x + 1 }; f(); f(); x
  1. 1
  2. 2
  3. 3
  4. Error
Why: <<- searches enclosing environments and updates the global x instead of creating a local copy. Two calls to f() increment it twice: 1 → 2 → 3.
Practice — How many times does "hi" print?
for (i in 1:4) { if (i == 3) next; print("hi") }
  1. 2
  2. 3
  3. 4
  4. 0
Why: next only skips the rest of that one iteration (i = 3); it does not stop the loop. "hi" prints for i = 1, 2, 4 — three times.

Sorting, ordering & ranking — the trio that gets confused

These three functions look alike and are the single most commonly confused topic in this unit. All three act on the same input; they answer three different questions.

Lists, factors, display & formatting

Lists: R's "container of anything"

Unlike a vector, a list can hold elements of different types and lengths — including other lists.

> student <- list(name = "Meera", marks = c(88, 91, 76), pass = TRUE)
> student$marks
[1] 88 91 76
> student[["name"]]
[1] "Meera"
> student["name"]      # single bracket -> a LIST of length 1, not the value itself
$name
[1] "Meera"
Exam trap — [ ] vs [[ ]] lst[i] always returns a list (a "slice" — same container type, fewer elements). lst[[i]] returns the element itself, unwrapped. This is the single most-tested list nuance in R exams.

lapply() applies a function to every element of a list and returns a list; sapply() does the same but simplifies the result to a vector or matrix when possible.

> nums <- list(a = 1:3, b = 4:6)
> lapply(nums, sum)
$a
[1] 6

$b
[1] 15
> sapply(nums, sum)
 a  b
 6 15

Factors: R's categorical variable

A factor stores categorical data as integer codes plus a levels table mapping codes back to labels — this is exactly how R represents nominal/ordinal variables for modelling.

> grade <- factor(c("B","A","C","A"), levels = c("A","B","C"))
> grade
[1] B A C A
Levels: A B C
> as.integer(grade)          # underlying codes, NOT the labels
[1] 2 1 3 1
> table(grade)
grade
A B C
2 1 1
Exam trap If a factor's levels happen to look numeric — e.g. factor(c("10","20","10")) — then as.numeric() on it returns the underlying codes (1, 2, 1), not the numbers you typed. The safe recovery path is as.numeric(as.character(f)).

For an ordinal variable (categories with a natural order), add ordered = TRUE: factor(x, levels = c("Low","Medium","High"), ordered = TRUE) — this then supports < and > comparisons between categories.

Unit 10

Basics of programming, scripts & functions

Anatomy of a function

> bmi <- function(weight_kg, height_m = 1.7) {   # height has a default
+   w_by_h2 <- weight_kg / height_m^2
+   round(w_by_h2, 1)
+ }
> bmi(70)              # uses default height
[1] 24.2
> bmi(70, 1.8)         # overrides it
[1] 21.6

A function's return value is either the argument to an explicit return(), or — if that's never reached — the value of the last evaluated expression in its body. Arguments in R are lazily evaluated: an argument expression isn't computed until it's actually used inside the function body, and R matches arguments by exact name, then partial name, then position — in that order.

Recursion vs. iteration

Unit 5 showed factorial written iteratively (a for loop). The same function can be written recursively, calling itself on a smaller sub-problem:

> fact <- function(n) {
+   if (n <= 1) return(1)      # base case
+   n * fact(n - 1)            # recursive case
+ }
> fact(5)
[1] 120

Every recursive function needs a base case that stops the recursion — omit it, and R eventually throws "C stack usage too close to the limit" once the call stack overflows.

Scripts

A script is simply a plain-text .R file containing a sequence of R statements, run top to bottom with source("myscript.R") or line-by-line in an editor. Q.68 — Arrange the following statements of an R program in correct order to make a valid program.

A. > y = x    B. > x <- c(1, -1, 3.5, 2)    C. [1] 1.00 1.00 12.25 4.00    D. > y^2

  2. A, D, B, C
  3. C, B, A, D
  4. B, A, D, C
Derivation
A program must first create x (B), then set y = x (A), then evaluate y^2 (D) — whose auto-printed result is C: 1²=1, (−1)²=1, 3.5²=12.25, 2²=4. Sequence: B → A → D → C, i.e. option 4.
Q.73 — Arrange the following statements of an R programme in correct order to make a valid program.

A. > y = A * x    B. > diag(y)    C. > x <- c(1, 2, 3)    D. [1] 1 20 27    E. > A <- matrix(c(1:9), 3, 3)

  2. E, A, C, B, D
  3. D, E, C, B, A
  4. E, C, A, B, D
Derivation

Environments, scoping & functional programming

An environment is R's name-to-value lookup table — every function call gets its own, and every environment (except the empty one) has a parent it falls back to when a name isn't found locally. This chain is what makes lexical scoping work: a function looks up free variables in the environment where it was defined, not where it was called from.

> x <- 10
> f <- function() {
+   x <- 20
+   g <- function() x       # g is defined inside f, so it sees f's x
+   g()
+ }
> f()
[1] 20
> environment(f)          # f's enclosing environment
<environment: R_GlobalEnv>

Closures

A closure is a function bundled with the environment it was created in — including any local variables that environment holds. This lets you build "function factories" that remember state between calls.

> make_counter <- function() {
+   n <- 0
+   function() {           # this inner function is the closure
+     n <<- n + 1           # <<- updates n in the ENCLOSING (counter) environment
+     n
+   }
+ }
> counter <- make_counter()
> counter(); counter(); counter()
[1] 1
[1] 2
[1] 3

Each call to make_counter() creates a fresh environment with its own n; a second counter would start again from 0, independent of the first.

Higher-order functions & functional style

R treats functions as ordinary values: they can be stored in variables, passed as arguments, and returned from other functions. The apply family (Unit 10) is the classic example; base R also has Map(), Filter(), and Reduce() for a more explicitly functional style.

> Filter(function(x) x %% 2 == 0, 1:10)     # keep elements matching a predicate
[1]  2  4  6  8 10
> Reduce(`+`, 1:5)                           # fold left: ((((1+2)+3)+4)+5)
[1] 15
> Reduce(function(a,b) a*b, 1:5, accumulate = TRUE)  # running product
[1]   1   2   6  24 120
Exam trap <- inside a function always creates or updates a local binding. <<- ("superassignment") instead searches enclosing environments for an existing binding of that name and updates the first one it finds — or creates one in the global environment if none exists anywhere in the chain. This is precisely the mechanism that makes the counter closure above work.

Error handling & debugging

R signals three severities of condition: a message (informational), a warning (something questionable happened, but execution continues), and an error (execution stops immediately). tryCatch() lets you intercept any of them.

> safe_divide <- function(a, b) {
+   tryCatch({
+     if (b == 0) stop("division by zero")
+     a / b
+   },
+   error = function(e) {
+     message("Caught: ", conditionMessage(e))
+     NA
+   })
+ }
> safe_divide(10, 2)
[1] 5
> safe_divide(10, 0)
Caught: division by zero
[1] NA

stop() raises an error (and accepts a formatted message); warning() raises a warning without halting execution; tryCatch() dispatches to whichever handler (error=, warning=, message=) matches the condition raised, and always runs its optional finally= block last, whether or not a condition was caught.

A lighter tool: try()

> result <- try(log(-1), silent = TRUE)   # warning, not error -- returns NaN, no need for tryCatch
> result <- try(stop("bad input"), silent = TRUE)
> class(result)
[1] "try-error"

try() is a lighter-weight alternative to tryCatch(): on error it returns an object of class "try-error" instead of stopping, which you then test for with inherits(result, "try-error").

Dates, times & a first look at time series

Base R has two core date/time classes: Date (calendar date, no time-of-day) and POSIXct (an exact instant, stored as seconds since 1 Jan 1970 UTC).

> d <- as.Date("2026-04-24")
> d + 10                       # date arithmetic is in DAYS
[1] "2026-05-04"
> format(d, "%d %B %Y")
[1] "24 April 2026"
> weekdays(d)
[1] "Friday"
> t <- as.POSIXct("2026-04-24 15:30:00", tz = "UTC")
> t + 3600                     # POSIXct arithmetic is in SECONDS
[1] "2026-04-24 16:30:00 UTC"
> Sys.Date(); Sys.time()        # today's date / current instant

The lubridate package (tidyverse) is the popular alternative for parsing (ymd(), dmy()), extracting components (year(), month(), wday()), and duration arithmetic that correctly accounts for leap years and daylight saving.

> sales <- ts(c(112, 118, 132, 129, 121, 135), start = c(2026, 1), frequency = 12)

     Feb Mar Apr May Jun
2026   6  14  -3  -8  14

Object-oriented programming: S3, S4 & R6

R has three overlapping OOP systems. Which one you meet depends on the package: base R and most CRAN packages use S3; Bioconductor and statistics-heavy packages favour the stricter S4; packages needing mutable, Python-style objects reach for the R6 package.

S3 — informal, and everywhere

An S3 object is just a base object (often a list) with a class attribute. "Methods" are ordinary functions named generic.class; calling generic(x) dispatches to generic.class(x) automatically.

> student <- list(name = "Anu", marks = 88)
> class(student) <- "student"
> print.student <- function(x, ...) cat("Student:", x$name, "-", x$marks, "marks\n")
> print(student)          # dispatches to print.student automatically
Student: Anu - 88 marks

This is exactly how summary(), plot(), and print() behave differently for a data.frame, an lm model, or a factor — each is S3 dispatch on the object's class.

S4 — formal, with validation

> setClass("Rectangle", representation(w = "numeric", h = "numeric"))
> setGeneric("area", function(shape) standardGeneric("area"))
> setMethod("area", "Rectangle", function(shape) shape@w * shape@h)
> r <- new("Rectangle", w = 4, h = 5)
> area(r)
[1] 20

S4 classes declare their slot names and types up front (representation()/setClass()), and slots are accessed with @ rather than $. Generics and methods are registered explicitly via setGeneric()/setMethod(), which gives R a chance to validate arguments before dispatch.

R6 — mutable, reference-based objects

> library(R6)
> Counter <- R6Class("Counter",
+   public = list(
+     n = 0,
+     increment = function() { self$n <- self$n + 1; invisible(self) }
+   ))
> c1 <- Counter$new()
> c1$increment(); c1$increment()
> c1$n
[1] 2
Exam trap S3 and S4 objects are normally copy-on-modify (R's default value semantics — changing a copy never affects the original). R6 objects are the exception: they use reference semantics, so c2 <- c1; c2$increment() also changes c1$n, because c1 and c2 point to the same underlying object.

The pipe |> takes the expression on its left and inserts it as the first argument of the call on its right — so df |> filter(x > 0) is exactly filter(df, x > 0). This reads as a left-to-right pipeline instead of nested function calls.

Exam-relevant fact Base R's |> (from R 4.1.0) and magrittr's %>% (used throughout the tidyverse before that) do the same basic job, but %>% supports extra features like the . placeholder for non-first-argument piping, which the native pipe historically lacked.

Data visualisation with ggplot2

ggplot2 implements the Grammar of Graphics: a plot is built by layering independent components onto a common set of aesthetic mappings, rather than calling one all-in-one plotting function as base R's plot() does (Unit 9).

LayerRole
ggplot(df, aes(x, y))the data and aesthetic mappings (what maps to x, y, colour, ...)
geom_point(), geom_line(), geom_bar(), geom_boxplot()the geometric layer — what shape represents the data
facet_wrap(~group)split into a panel per group
labs(), theme()titles/labels, and non-data styling
 
> library(ggplot2)
> ggplot(df, aes(x = state, y = score)) +
+   geom_boxplot(fill = "lightblue") +
+   labs(title = "Score by state", x = NULL, y = "Score")

Layers are combined with +, not the pipe — a common source of "non-numeric argument" errors when a stray |> or %>% slips into a ggplot chain. Aesthetic mappings set with aes() vary per data point (e.g. colour by group); fixed visual properties (e.g. one colour for everything) are set outside aes(), as a plain argument to the geom.

Exam trap aes(colour = "blue") does not make the points blue — it creates a legend with one category literally named "blue" and maps it to ggplot's first default colour. To fix a colour, set it outside aes(): geom_point(colour = "blue").

Descriptive statistics & probability distributions

Unit 3 covered the basic descriptive functions (mean(), median(), sd()...). R's stats package (loaded by default) additionally provides a complete family of functions for every standard probability distribution, following a consistent d/p/q/r naming convention.

PrefixGivesExample
ddensity / point probabilitydnorm(0) → height of the standard normal curve at 0

qquantile — the inverse of pqnorm(0.975) → ≈ 1.96

The same four-letter pattern applies to every distribution: *binom (binomial), *pois (Poisson), *unif (uniform), *exp (exponential), *t, *chisq, *f, and more.

Exam-relevant fact set.seed(n) makes R's pseudo-random draws (rnorm(), sample(), runif(), ...) exactly reproducible — the same seed always regenerates the same sequence, which is why it's standard practice at the top of any script that uses randomness.

Hypothesis testing in R

R's standard test functions all share a common shape: they return an htest object, printed as a compact summary that includes the test statistic, degrees of freedom, and (critically) the p-value.

FunctionTests
t.test(x, y)difference in means (one-sample, two-sample, or paired with paired=TRUE)
chisq.test(table)independence / goodness-of-fit for categorical data
aov(y ~ group, data)ANOVA — difference in means across 3+ groups
wilcox.test(x, y)non-parametric alternative to t.test()
shapiro.test(x)tests whether x looks normally distributed
cor.test(x, y)significance of a Pearson/Spearman correlation
 
> kerala <- c(78, 91, 85, 88, 76)
> tn     <- c(65, 70, 68, 72, 60)

data:  kerala and tn

By convention, a p-value below a chosen significance level (commonly 0.05) leads to rejecting the null hypothesis. Extract just the number with t.test(kerala, tn)$p.value rather than reading it off the printed summary.

Exam trap R's t.test() defaults to Welch's t-test (which does not assume equal variances) rather than the classic Student's t-test. Pass var.equal = TRUE explicitly to get the equal-variance version taught in most introductory statistics courses.

Correlation & linear regression

> hours  <- c(1, 2, 3, 4, 5, 6)
> scores <- c(52, 58, 63, 69, 77, 80)
> cor(hours, scores)                    # Pearson correlation coefficient
[1] 0.9959099
> model <- lm(scores ~ hours)            # fit: scores = intercept + slope*hours
> coef(model)
(Intercept)       hours
   45.66667     5.62857
> summary(model)$r.squared
[1] 0.9918365
> predict(model, newdata = data.frame(hours = 7))
      1
85.06667

R's model formulas use y ~ x to mean "model y as a function of x"; y ~ x1 + x2 adds a second predictor for multiple regression, and y ~ . means "use every other column in the data frame as a predictor." lm() fits by ordinary least squares; coef(), summary(), residuals(), and predict() all work directly on the fitted model object.

Exam-relevant fact summary(model) reports both R² ("Multiple R-squared") and adjusted R². R² only ever increases as you add predictors, even useless ones — adjusted R² penalises extra predictors and is the fairer number for comparing models with different numbers of terms.

glm() extends lm() to response variables that aren't normally distributed continuous values — most commonly a binary outcome (logistic regression) or count data (Poisson regression) — by adding a family= argument that specifies the error distribution and link function.

Introduction to machine learning concepts

Machine learning in R follows the same core workflow regardless of which model you use: split your data, fit ("train") a model on one part, and check how well it generalises on data it hasn't seen.

ConceptMeaning
Supervised learningthe training data has known labels/outcomes (e.g. regression, classification)
Unsupervised learningno labels — the algorithm finds structure on its own (e.g. clustering, PCA)
Train/test splitfit the model on a training subset, evaluate on a held-out test subset it never saw
Overfittingthe model memorises training-set noise and performs worse on new data
Cross-validationrepeating the train/test split k times to get a more reliable performance estimate
 
> set.seed(42)
> n <- nrow(iris)
> train_idx <- sample(seq_len(n), size = 0.7 * n)    # 70% for training
> train <- iris[train_idx, ]
> test  <- iris[-train_idx, ]                        # the remaining 30%
> nrow(train); nrow(test)
[1] 105
[1] 45
TaskCommon metric(s)
Classificationaccuracy, precision, recall, F1, a confusion matrix (table(predicted, actual))
RegressionRMSE, MAE, R²
Clusteringwithin-cluster sum of squares, silhouette score

The caret and newer tidymodels packages standardise this workflow (splitting, training, tuning, and evaluating) across dozens of underlying model engines, so you don't have to learn each algorithm's package interface separately.

Exam trap Never evaluate a model's performance on the same rows it was trained on — that number is optimistic and doesn't reflect real-world accuracy. The test set must be held out before any fitting happens, which is exactly why train_idx is drawn first, above.

ML models in R: kNN, trees, forests & clustering

k-Nearest Neighbours (classification)

> library(class)
> pred <- knn(train = train[, 1:4], test = test[, 1:4],
+              cl = train$Species, k = 5)
> mean(pred == test$Species)          # accuracy
[1] 0.9555556

Decision trees & random forests

> library(rpart)
> tree <- rpart(Species ~ ., data = train, method = "class")
> table(predict(tree, test, type = "class"), test$Species)   # confusion matrix

> library(randomForest)
> rf <- randomForest(Species ~ ., data = train, ntree = 200)
> importance(rf)                       # which predictors mattered most

A single decision tree (rpart) splits the data recursively on the predictor that best separates the classes at each step; a random forest averages many such trees, each grown on a random subset of rows and predictors, which usually generalises much better than any one tree alone.

k-Means (unsupervised clustering)

> km <- kmeans(iris[, 1:4], centers = 3, nstart = 10)
> table(km$cluster, iris$Species)
> km$centers                          # the 3 cluster centroids

kmeans() needs no outcome column — it groups rows purely by proximity in predictor space. centers= sets the number of clusters k; nstart= reruns the algorithm from several random starting points and keeps the best result, since k-means can converge to a poor local optimum from a single random start.

Exam-relevant fact kNN and k-means share a name but are unrelated: kNN is supervised classification (it needs labels, and k = number of neighbours consulted per prediction); k-means is unsupervised clustering (no labels, and k = number of clusters to form).
